# Conceptual review: main drift (3809dfe5c6 -> a032e2fd7d) vs our 760/979/980 series

Scope: what actually changed in openwrt **main** between our old branch's merge-base
(`3809dfe5c6`, 2026-08-28) and the 6.18.53 bump head (`a032e2fd7d`, 2026-09-22),
in our areas or adjacent — and what that means **semantically** for the port,
not just "does the text patch apply".

459 commits; kernel base moved **6.18.44 -> 6.18.53**; mediatek + generic
pending-6.18 touched heavily.

---

## 1. New / changed base patches that overlap our IP

### 1.1 `702-net-ethernet-mtk_eth_soc-enable-threaded-NAPI.patch` (generic)

```
+	eth->dummy_dev->threaded = 1;
+	strcpy(eth->dummy_dev->name, "mtk_eth");
 	netif_napi_add(eth->dummy_dev, &eth->tx_napi, mtk_napi_tx);
```

- Sets `threaded = 1` (and the dev name) in **main's probe** — the same line our
  `760-22` sets and our `980` reorders.
- **Semantics:** main WANTS threaded NAPI (Felix: avoid pinning on CPU0). Our
  A/B rejected softirq (`threaded = 0`), so **main and we agree**. `threaded=1`
  is now also a base property; our `760-22`/`980` duplicate it (cosmetic).
- **Risk:** low; both set the same value, no fight (prepare clean).

### 1.2 `738-01` / `738-02` (generic, present in both — watch)

- `738-01 reduce-rx-ring-size-for-older`: drops `rx.dma_size` for older SoCs
  (512 for mt7621/22/23/29/7981, **1K for mt7986**, 256 for rt5350).
  **mt7988 not listed** -> our 7988 ring sizing unaffected.
- `738-02 do-not-enable-page-pool-sta...`: wraps page-pool stats in
  `CONFIG_PAGE_POOL_STATS`. Orthogonal to our `760-28` page_pool **gate**, but
  adjacent in `mtk_page_pool_enabled`'s neighbourhood -> re-check on future
  page-pool changes.

### 1.3 `737-09 improve-probe-deferal` (generic — probe, our area)

- Splits MAC-address assignment out of `mtk_add_mac()` into a new
  `mtk_mac_assign_address(eth, i, test_defer_only)`, pre-checking all nvmem
  providers before any random-MAC fallback.
- **Adjacent to our `979`** (stable MAC via nvmem). 979 is **DTS-only**, so no
  text collision — but the **behaviour it relies on** now lives in
  `mtk_mac_assign_address`, not `mtk_add_mac`.
- **Semantics:** 979's contract (nvmem provider preprogrammed; driver
  probe-defers) is *better* satisfied now. Action: re-verify on device.

### 1.4 `795-01..06` (generic — PPE/DSA TX queue map)

- `795-04 per-SoC QDMA TX queue count with register paging`, `795-05
  per-conduit DSA user-port queue map`, `795-06 use DSA queue map in TX path`,
  PPE offload port/tport fixes.
- **Already in our old branch** (identical filenames on both sides) -> no new
  conflict; the 760 series sits on identical ground.

## 2. Sublevel drift 6.18.44 -> 6.18.53 in *our* functions

### 2.1 `2ff6d12554 generic: restore EEE support on mt753x and mtk_eth_soc`

- Fills `phylink_config.lpi_interfaces` (backport of upstream `3c18e3c9a54e`),
  plus adaptations to the other mtk_eth_soc pending patches (702, 732-00,
  732-03, 737-09, 738-01, ...).
- **Semantics:** a *phylink mac_config / EEE* change — the same region our
  `760-22` (`mtk_mac_config` -> `mtk_set_mcr_max_rx`) and `760-27` (per-open
  `max_mtu`) live in. It does **not** touch RSS, rings, rx_buf_len, MTU or
  page_pool, so the functional path is unaffected.
- It is exactly the kind of change that shifts hunk context (our only text
  conflict was CAPS/EEE). Treat the EEE region as "hot" for future rebases.
- `MTK_GMAC_EEE` is now in `MT7981_CAPS`; that is *why* `760-22/23` needed the
  `MTK_GMAC_EEE` hunk fix.

### 2.2 phylink/PCS plumbing

`328acd4e9d remove Kconfig.orig from USXGMII PCS`, `b6a035fc2b fwnode phylink
PCS`, `2de0893dd2 PSGMII in-band`, `77824a92b8 link PCS list before initial
phylink config`.

- `760-27` decides 9K-vs-2K `max_mtu` from the interface mode
  (`mtk_interface_mode_is_xgmii`), relying on `mac->interface` being valid at
  `mtk_open`/`mac_config`. Main's "link PCS list before initial phylink config"
  makes that ordering *more* deterministic — a net improvement, but untested
  by us on this branch.

## 3. Main changes we don't have and should consciously ignore

- **`699-netfilter-flowtable-set-out-ifindex...`** + `xt_FLOWOFFLOAD`/flow
  offload fixes (hauke): the **software** flowtable path (R4-Pro #27340). Our
  fix (keep DSA conduits out of flowtable devices) still stands; no code
  overlap.
- `505-ksmbd-revert...`, LoongArch/MIPS vDSO — irrelevant.
- `197-arm64-dts-mediatek-mt7986-correct-timer-frequency.patch` removed
  (superseded by `f36067d4e9 correct MT7986 system timer rate`); mt7986-only.

## 4. Numeric / structural drift ("patch applies" is misleading)

- `737-08/09/10` in main == our `737-08/09` + a renumbered dt-bindings patch.
  Our `760-2x` sit above main's highest 7xx in our tree, so no clash — but the
  numbering is only *locally* stable. Any future main patch in the 760-779 band
  collides with our `760-21..29`.
- `979`/`980` are our own numbers (free), but historically reused for two
  different things (979 = stable-MAC dts, 980 = dummy-device).
- `050-...-5v-fan...` slot is free in main's mediatek `05x` band.

## 5. What "it compiles and the patch applies" did NOT prove

Established only: (1) text hunk context still matches after `.44->.53`;
(2) the C compiles against .53 APIs. Not established:

- **(a) `mtk_mac_config()` ordering vs `rx_buf_len`.** The 760-29 invariant
  ("mac_config never lets a MAC accept a frame the rings can't take") rests on
  `rx_buf_len` being derived in `mtk_dma_init()` before any `mac_config` runs,
  and on `mac_config` writing `mtk_set_mcr_max_rx(mac, eth->rx_buf_len)`.
  Main's EEE/PCS changes touched `mtk_mac_config`'s neighbourhood and phylink
  config ordering. **Runtime-unverified.**
- **(b) probe-defer rework vs our dummy-device reorder.** `737-09` moved MAC
  assignment; `980` reorders `alloc_netdev_dummy` + `netif_napi_add` before
  `register_netdev`. Both edit the same tail of `mtk_probe`; clean apply does
  not prove the race `980` closes is unchanged, nor that the new defer path
  doesn't re-open a window.
- **(c) threaded NAPI ownership.** Main sets `threaded = 1`; we additionally
  hang 4 RSS rings on that dummy dev. With multiring, the
  kthread-per-ring model vs main's single-ring assumption may differ in CPU
  placement. Measured on .44 only.
- **(d) page_pool gate vs 738-02 / CONFIG_PAGE_POOL_STATS.** Jumbo-gate
  disables page_pool -> stats path unused, 9K frag path used. Untested combo.
- **(e) `795-04` per-SoC TX queue count / QDMA paging.** Main's paging logic is
  in `mtk_start_dma`/`mtk_tx_alloc`; our 760-22/29 touch `mtk_dma_init`
  (calls `mtk_tx_alloc`) and `mtk_start_dma` is on the ring stop/start path.
  Untested interaction with our ring realloc.

## 6. Recommended verification before trusting this branch

> Results of running these checks on hardware are in
> `6.18.53-rebase-verification.md` (all invariants passed on 6.18.53).


1. Boot (config-preserving): eth0/1/2 present; 4 RSS rings fire
   (`/proc/interrupts`); `rx buffer length` grow at boot; `carrier_changes == 1`.
2. Live `ip link set mtu` shrink/grow on a running conduit (exercises 760-29 +
   `mac_config` ordering on the new base).
3. 8K ping + iperf ~9.8G at 9000; the 1500 ingress shape.
4. Stable MACs survive the `737-09` defer rework: no
   `generated random MAC address` on boot.
5. Sanity the 10G combo path (`eth1` usxgmii, `eth2` 10gbase-r) after the
   PCS/phylink changes.

## 7. Bottom line

Nothing in the main drift **contradicts** our design. The real overlap is
`702` (threaded NAPI — we agree), `2ff6d12554` (EEE/`lpi_interfaces` — why the
CAPS hunk moved), `737-09` (probe deferal, adjacent to 979/980), and the
pre-existing 795/738. The rebase is textually and compilation-correct, but the
**runtime invariants (a)–(e) are unverified on 6.18.53** — they were only ever
measured on .44. That is the gap the "applies cleanly" pass could not cover.
