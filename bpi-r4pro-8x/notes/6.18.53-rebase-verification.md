# 6.18.53 rebase: hardware verification results

Branch: `bpi-r4pro-8x-multiring-6.18.53`
Base: openwrt main + `kernel: bump 6.18 to 6.18.53` (PR #25331 head `a032e2fd7d`).
Kernel: **6.18.53**. Image revision at test time: **r599-1f96c1c5ae**.

Method: build via `bpi-r4pro-8x/build.sh` (-j28), stage to TFTP, boot the
recovery ITB over TFTP from U-Boot (**RAM only, no NAND write**), then run the
invariant + throughput tests identified in `6.18.53-rebase-conceptual-review.md`
§6. These are the checks that the "patch applies / compiles" pass could not
cover; all of them were previously only ever measured on 6.18.44.

## 1. Boot and probe

- Boots; `Linux 6.18.53`; all three MACs probe
  (`eth0/eth1/eth2: mediatek frame engine ... irq 104`).
- mt7530 (tree 1) and MxL86252 (tree 0) come up; WLAN (`mt7996e`) and the NVMe
  kmod present; `Aeonsemi recovery: stale cached PCS ID refreshed` on
  `mdio-bus:18/1c` is the expected as21xxx warm-reboot workaround (970).
- No `pstore`/recovery detour; NAND untouched.

## 2. Invariants from the review (§5 a-e)

| # | invariant | result |
|---|---|---|
| — | stable MACs under the new `737-09` probe-defer path | **PASS** — `00:0c:43:36:2f:60/61/62`, `generated random MAC` count **0** |
| — | RSS rings allocated and firing (760-22) | **PASS** — 4 IRQs (`PDMA RX 0` + `RSS RX 1/2/3`) all counting |
| (c) | threaded NAPI present | **PASS** — 5 `napi/mtk_eth-0` kthreads |
| (a) | `mtk_mac_config` vs `rx_buf_len` ordering exercised by live MTU changes (760-29) | **PASS** — `1536 -> 9216`, `9216 -> 1536`, `1536 -> 9216` all logged, **no flap** (`carrier_changes` stayed constant), **0** `skb_over_panic`/`WARNING` |
| (d) | page_pool jumbo gate (760-28) vs 738-02 | no anomaly observed at 9K/1500 line rate |
| (e) | `795-04` QDMA paging vs ring stop/start | no anomaly observed |

Ring-sizing sanity observed live: with **only eth2** lowered to 1504 while other
ports were still 9000, **no realloc happened** — correct, since `mtk_max_gmac_mtu()`
was still 9K and the rings are shared/sized to the largest MTU. A real
`9216 -> 1536` only fired once *all* ports dropped.

## 3. Throughput (management cable on `lan6`, 10 G, MxL/eth2 path)

iperf3, `-P4`, `-t 8`:

| direction | MTU 9000 | MTU 1500 |
|---|---|---|
| ingress (changwang -> banana) | **9.88 Gb/s** (7 retr) | 4.47 Gb/s |
| egress (banana -> changwang) | **9.89 Gb/s** (0 retr) | 9.38 Gb/s |

- Line rate both directions at 9K.
- 8K DF ping both directions: 3/3, ~0.3 ms.
- The 1500 shape (ingress ~4.5 G / egress ~9.4 G) matches the 6.18.44
  measurements exactly -> **no throughput regression from the .53 rebase**.
- Note: an earlier run showed ~940 Mb/s because the management cable was on
  `lan5` (internal mt7530, 1 G), not `lan6`. That is a physical-path fact, not a
  driver limit; `bridge fdb` is the reliable way to tell which port the cable is on.

## 4. Customizations present on this branch

- `760-21..29` RSS / multi-ring NAPI / ethtool surface / 9K jumbo /
  runtime rx-ring realloc worker.
- `979` stable MAC via nvmem, `980` NAPI dummy-device reorder.
- uboot `472`: combo ports default to copper, PCIe Gen3 + NVMe.
- dts `973`: `gmac1` kept as `eth1`.
- `050`: 5V-fan-on-12V-rail curve.
- Project docs + `config.seed` from the parent branch.

(Per request, the recovery/TFTP uci-defaults script changes are not documented
here.)

## 5. Outstanding before trusting this branch as the new baseline

- A **flashed** (NAND/eMMC) boot has not been exercised; only the recovery
  initramfs. Re-run §2 after a config-preserving sysupgrade.
- `eth1` was observed linking at **1000 Mb/s** in one boot (usxgmii negotiating
  1G with the current peer) — worth checking the 10G combo link on a flashed boot.
- CI status on the branch head to be confirmed green.
